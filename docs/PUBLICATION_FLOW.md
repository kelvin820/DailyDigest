# 審閱、發布與已出刊日曆

目前採 Git 版本化發刊：刊物及檔案有雜湊、版本與發布紀錄，由 Vercel 隨 Git commit 原子部署。沒有宣稱已寫入 Supabase。網站閱讀與審查頁目前公開，DayDay 帳號仍延後；變更首頁的權限由 GitHub 保護。

## 操作流程

1. 製作：在 GitHub 的 **Generate review edition** 手動執行核對過的來源計畫。今天製作 `2026-11-19-r2` 後，經來源與分級校稿依序修訂到 `2026-11-19-r5`；歷次草稿和原始模型意見都保留。修訂沿用已核准圖片，不重複生圖。沿用已設定的 NVIDIA Secret；工作流保留原始回覆與用量。重跑會按建立時間選最新 artifact，凍結事實並重用成功步驟；未知用量或遺失圖片預留會停止，不自動重複花費。
2. 審閱：新稿成功後部署到 `/review`，首頁仍保留目前刊物。查看三版、不同程度的單字、分齡插畫、來源、模型修訂項目與六份兩頁 PDF。
3. 核准：審查頁的「前往核准發布」開啟 GitHub **Approve and publish edition**。點 Run workflow，填入審查頁的期刊 ID 與完整「此版編號」，勾選已審閱。GitHub 需要此 repo 的操作權限；一般訪客無法透過公開頁發布。
4. 發布：工作流重新核對同一份稿件、來源與圖片雜湊、十二份模型審稿，再生成六份正式 PDF。任一檢查失敗，首頁保持原樣。全部成功才提交發布紀錄，待 Vercel 建置成功後，訪客重新整理即看到最新已發布日期。
5. 舊刊：發布紀錄不刪除。`/issues` 的月曆和日期清單只顯示真正發布的日期。同一天多次修訂顯示最新版；未發布的試閱稿不會冒充歷史出刊。

日曆先採「月曆＋清單」：月曆方便按日選擇，清單在手機與期數少時也好找。沒有刊物的日期不提供連結，不會用假資料填滿。

## 本次試發與後續

使用者要求今天跑通一次並換掉試閱首頁，因此可由開發代理完成本次檢查與試發，紀錄為 `developer_test_release`，不宣稱使用者已逐篇人工審閱。之後透過上述 GitHub 勾選核准會記錄 `github_manual`、執行者與審閱版本。

目前沒有啟用每日排程、付費新聞 API、Google 生圖或郵件通知。來源計畫仍是實際讀取後準備的底稿，不代表自動新聞發現已驗收。未來啟用 DayDay 登入時，再以同一份不可變版本與發布檢查保護審查頁、整合站內核准，並把之後未公開的草稿切到私有儲存；目前已公開的草稿不會因為鎖頁而從 Git 歷史消失。不需要重寫刊物歷史。

正式 Supabase 路徑仍保留，服務憑證與第十五份 migration 等需求見 SETUP.md；本次網站試發不依賴這些憑證，也沒有假裝完成其資料庫驗收。
